Workflow specifications

Trace each interaction from its entry condition through its service writes and recovery path. Screen designs are available in the student app and staff console chapters.

Read each flow as a recipe

Entry means what starts the flow. Interaction means what the person sees and taps. Service and storage means the API call and saved record. Alternate path means what to show if something goes wrong.

For example: a student taps Save and continue → the phone sends the chosen option → the API saves it → the phone shows the next question. If saving fails, keep the selected option visible and offer Retry.

The student's path in order

  1. Open the exam app and sign in with a demo account.
  2. Check the profile and choose at least one quality.
  3. Start Baseline (stage 0). Practice 1–4 unlock one at a time.
  4. Save each answer; leave and resume if needed.
  5. Review, submit once, then read the score and progress.

Open a section below only when you are implementing that part. Try the student preview first if these steps are unfamiliar.

Sign in and return to the right stage
  1. Entry: the student opens the app, an Exam icon, or a practice reminder.
  2. Read a saved session token. If it is valid, load the student with GET /v1/me. Otherwise show sign-in.
  3. For demo sign-in, POST /v1/challenges with demo-a or demo-b. Then POST /v1/sessions with challenge ID and code 246810.
  4. If the student opened a Practice 1 reminder, remember only stage 1 while they sign in. Check if it is allowed before opening it.
  5. Wrong code: show an inline message and let them retry. Expired token: ask them to sign in again. Sign out: DELETE /v1/session and clear the saved token.
Check profile and choose qualities
  1. Show the student’s name, grade, school, and language from GET /v1/me. Load allowed schools with GET /v1/schools.
  2. If the student edits details, check required fields and send the full profile with PATCH /v1/me. Show the first invalid field if the API rejects it.
  3. Load 24 sample qualities with GET /v1/qualities. Group them into four dimensions. The student must choose at least one.
  4. Send chosen IDs with PUT /v1/selections. Later selections add to the plan. They do not change an attempt already started.
  5. If the network fails, keep the form values on screen and let the student retry.
Show the five stages
  1. Show Baseline, then Practice 1, 2, 3, and 4. These are stage numbers 0–4.
  2. GET /v1/stages returns the state and times. A completed stage shows Result. A started but unfinished stage shows Resume. An available stage shows Start.
  3. Practice N stays locked until the previous stage has been submitted. A stage can also be closed because its time window ended.
  4. When Start or Resume is tapped, POST /v1/attempts with the stage number. Starting the same stage again returns the existing attempt ID.
  5. If there is no selected quality, send the student to the quality screen.
Answer questions and save a draft
  1. GET /v1/attempts/{id} returns the fixed list of questions and any saved choices. Show one question at a time.
  2. When a choice is tapped, keep it selected. On Save and continue, PUT /v1/attempts/{id}/answers with that question ID and the choice number.
  3. Wait for a successful API response before showing the next question. A choice is numbered from 0, so the first option is 0.
  4. If saving fails, keep the choice visible with an Unsaved message and Retry button. On reopen, read the attempt again and resume at the first unanswered question.
  5. Allow the student to go back and change a saved choice before submission.
Review, submit, and show result
  1. Show each question and its saved choice. Allow Edit before final submission.
  2. When the student confirms, POST /v1/attempts/{id}/submit. Disable the button while the request is in progress.
  3. The API checks that all answers exist, calculates scores, and saves the submission time together. The phone displays the returned result.
  4. If the response is lost, GET /v1/attempts/{id} before trying again. A repeat submit returns the original result.
  5. If the API says incomplete, return to the unanswered item. If the stage closed before submission, show the closed state. A submitted attempt cannot be edited.
Read progress
  1. GET /v1/progress returns the student’s stage history. Show the stage, date, earned points, possible points, and percentage.
  2. Only submitted stages have scores. Do not display an unfinished draft as a result.
  3. A quality added after Baseline has no Baseline score. Show a dash for that missing value.
  4. For a stage percentage, add all earned points, add all possible points, then divide. Round only when displaying.
Staff roster and school access — planned
  1. A school viewer may see one allowed school. A programme administrator can see the allowed programme scope and add a synthetic student.
  2. The future staff API must decide the allowed scope from the staff session. A school dropdown on the screen is not enough to protect records.
  3. Show an empty roster message when no students match. Reject a school outside the staff member’s allowed scope.
  4. Keep historical stage membership if a student changes schools, so past reports stay correct.
Staff question editing — planned
  1. An administrator writes a draft question in English and Telugu with translated answer options and one correct choice.
  2. Preview both languages before publishing. Saving a draft must not replace a question already used by a student.
  3. Publishing makes a new version for future attempts. Old attempts keep their original question version and result.
  4. Show errors for a missing translation or invalid correct choice.
Staff stage schedule — planned
  1. An administrator enters opening and closing times for one stage. The opening must be before the closing.
  2. Store times in UTC. Show local time to students. At the exact closing time, saving or submitting is no longer allowed.
  3. Use a revision value so an old staff screen cannot overwrite another person’s newer schedule.
  4. Submitted results remain readable after closing.
Staff reports and CSV — planned
  1. Filter by allowed school, district, stage, and dates. Apply the same filters to the screen and downloaded CSV.
  2. Show counts as well as percentages: for example, 1 of 2 eligible students submitted Baseline = 50%.
  3. Only compare a quality when the same learner has results for both stages. Show a dash when there is no matched result.
  4. If no students match, show an empty report and a CSV with headers. Never let a school viewer request another school.
Update the local database after a merge
  1. When a reviewed SQL file arrives in main, bring your branch up to date and run npm run db:refresh.
  2. The migration runner applies only new files. Existing local drafts and scores remain.
  3. If a migration fails, the database change is rolled back. Read the error, fix the new migration, and retry.
  4. Do not edit a migration that was already merged. Add a new numbered file for a correction. See Run and update locally for commands.

Make screens easy to use

On a phone, use one column. Keep the stage name, question number, answer choices, and main button easy to find. Make every touch target at least 48 logical pixels. Leave space around the keyboard and phone edges. Support larger text and screen readers. Announce save errors in words. When a student returns from Review to edit a question, return focus to that question. Do not use color alone for Locked, In progress, or Complete. Provide the same meaning in text and in both supported languages. On a small staff screen, let wide tables scroll sideways.
