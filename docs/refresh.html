Refresh & migrate

A single Docker container runs PostgreSQL 17. Git distributes schema and fixture changes. Each developer keeps their learners, attempts and answers in a local Docker volume.

Feature branchAdd numbered SQL and an upgrade case
MainMerge reviewed migration files
Local checkoutFast-forward, start Docker service, apply pending SQL
Local volumeKeep drafts and results across sessions

First run

Use Docker with Compose v2 and Node 22.13+ from the 22.x line. Open a terminal in the extracted repository. The compose service binds only to loopback, at port 55432. The API uses the database assessment and the application schema exam.

npm ci
npm run db:start
npm run db:refresh
npm test
npm start

Inspect the database with the client included in the container:

docker compose exec db psql -U exam_owner -d assessment
SHOW server_version;
SELECT name, applied_at FROM public.exam_migrations ORDER BY name;
SELECT count(*) FROM exam.qualities;  -- 24
\q

After changes merge to main

From a clean main checkout with origin configured, stop the API, start Docker, and run:

npm run sync
npm test
npm start

Sync fetches origin/main, fast-forwards the checkout, starts the database and applies pending migrations. A dirty tree or diverged main stops the update. For a ZIP without origin, use the first-run commands. On a feature branch, merge origin/main into the branch, run npm ci if the lock file changed, then run db:start and db:refresh. The default Compose project shares one sandbox volume across branches on a machine. A checkout missing migrations already applied to that volume will refuse to refresh.

Make a schema or fixture change

  1. Sync main and create a branch. Add the next consecutive file in db/migrations/, such as 0004_feedback.sql. Qualify application tables with exam..
  2. Add new fixtures with stable IDs. For a new required field, add a default or nullable column, backfill existing rows, then enforce the constraint. Keep published questions referenced by old attempts.
  3. Run refresh twice. Add a populated upgrade case to the tests. CI starts the same Docker service and verifies clean migration, upgrade, rollback, RLS and the exam journey.
  4. Commit the migration, API changes and tests. If another branch merged the same number first, renumber the unpublished migration and test against current main. Keep merged migration files immutable.
-- Example migration
CREATE TABLE exam.feedback_bands (
  id text PRIMARY KEY,
  min_percent integer NOT NULL CHECK (min_percent BETWEEN 0 AND 100),
  en text NOT NULL,
  te text NOT NULL
);

Failure and recovery

The runner locks the migration transaction, checks PostgreSQL major version 17, verifies filenames and SHA-256 hashes against public.exam_migrations, and commits pending SQL with its ledger entries. A SQL failure rolls back the batch. Keep transaction control outside migration files. If a checksum differs, restore the original merged file and express the correction in a new migration.

# Stop the API before a code or schema change
# Back up the local sandbox to a fresh file outside the repository
docker compose exec -T db pg_dump -Fc -U exam_owner assessment > ../exam-backup.dump
# Inspect a backup before restoring it
docker compose exec -T db pg_restore -l < ../exam-backup.dump
# Restore into a NEW database on this same sandbox cluster
docker compose exec -T db createdb -U exam_owner assessment_recovery
docker compose exec -T db pg_restore -U exam_owner -d assessment_recovery --exit-on-error < ../exam-backup.dump

npm run db:stop stops the container and retains the volume. npm run reset removes the exam Compose volume and rebuilds it from the checked-in migrations. Use reset only for disposable local work. The earlier file-based starter's practice records stay in their old file; this setup seeds a fresh PostgreSQL database.
