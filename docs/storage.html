Data model & scoring

The starter runs PostgreSQL 17 in a dedicated Docker container on 127.0.0.1:55432. All clients use HTTP. This keeps the student feature portable when the platform team later maps the contract into its database.

Relationships

School 1 ─── many Student 1 ─── many Attempt (unique per student + stage)
                     │                    │
                 Selection             Attempt item ─── Question version
                     │                    │                     │
                   Quality ───────────────┴── Score by quality  │
                     └──────────────────────────────────────────┘

In the schema an attempt item references an attempt and question. A score references an attempt and quality. Dimension and district are fixture codes. The exact constraints are in the executable schema below.

Inspect the PostgreSQL schema
CREATE SCHEMA exam;
SET search_path = exam;
CREATE TABLE schools(id TEXT PRIMARY KEY, district TEXT NOT NULL);
CREATE TABLE students(id TEXT PRIMARY KEY, school TEXT NOT NULL REFERENCES schools, name TEXT NOT NULL, grade TEXT NOT NULL, locale TEXT NOT NULL CHECK(locale IN ('en','te')));
CREATE TABLE qualities(id TEXT PRIMARY KEY, dimension TEXT NOT NULL, en TEXT NOT NULL, te TEXT NOT NULL);
CREATE TABLE selections(student TEXT REFERENCES students, quality TEXT REFERENCES qualities, PRIMARY KEY(student,quality));
CREATE TABLE questions(id TEXT PRIMARY KEY, quality TEXT NOT NULL REFERENCES qualities, en TEXT NOT NULL, te TEXT NOT NULL, options JSONB NOT NULL, correct INTEGER NOT NULL CHECK(correct IN (0,1)));
CREATE TABLE attempts(id TEXT PRIMARY KEY, student TEXT NOT NULL REFERENCES students, stage INTEGER NOT NULL CHECK(stage BETWEEN 0 AND 4), created TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP, submitted TIMESTAMPTZ, UNIQUE(student,stage));
CREATE TABLE items(attempt TEXT REFERENCES attempts, question TEXT REFERENCES questions, choice INTEGER CHECK(choice IN (0,1)), PRIMARY KEY(attempt,question));
CREATE TABLE scores(attempt TEXT REFERENCES attempts, quality TEXT REFERENCES qualities, earned INTEGER NOT NULL, possible INTEGER NOT NULL, PRIMARY KEY(attempt,quality));

CREATE TABLE stage_windows (
  stage INTEGER PRIMARY KEY CHECK(stage BETWEEN 0 AND 4),
  opens_at TIMESTAMPTZ NOT NULL,
  closes_at TIMESTAMPTZ NOT NULL CHECK(closes_at > opens_at)
);
CREATE INDEX questions_by_quality ON questions(quality);

Session and row access

The server verifies the mock bearer and begins a PostgreSQL transaction. It assumes the restricted exam_runtime role and sets the learner ID for the transaction. Database policies scope profiles, selections, attempts, answers and scores to that identity. The API returns question text and options to the phone. Only the backend reads answer keys.

Draft and submission lifecycle

  1. Start stage
  2. Snapshot selected questions
  3. Save answers
  4. Review completeness
  5. Commit scores and timestamp
  6. Read immutable result

The unique (student, stage) constraint makes a second start resume the same attempt. A draft answer is uniquely addressed by attempt and question. Null means unanswered. The API serializes mutations for a learner with a PostgreSQL transaction advisory lock. A repeated submit reads the stored result after the first transaction commits.

For each quality: possible = count(snapshot items)
                  earned   = count(choice == correct index)
Stage percentage = round(100 × sum(earned) / sum(possible))
Change           = current percentage − earlier percentage (points)

Demo rubric: one point per correct response, no partial credit, one submission per stage. Show “Keep practising” below 100% and “All items correct” at 100%. Persist the scoring version before pilot. This demo rubric and the repeated synthetic question require curriculum approval.

Stage windows and eligibility

Seed all five windows open for ordinary demos. Gate practice N on submission of N−1. Use a controllable UTC clock for boundary tests. At or after close, keep drafts readable and reject edits or submission with 409 window_closed. Previously submitted results stay readable. Added qualities enter the next newly created attempt. Use missing for earlier stages without that quality.

Reporting definitions

MeasurePopulation and calculation
EligibleFixture roster in the selected school/district at stage opening. Snapshot roster membership per stage before supporting transfers.
Participation and completionDistinct eligible students with an attempt created or submitted respectively in the UTC range [from,to), divided by eligible count. Display numerators alongside percentages.
Selected and practisedRank qualities by distinct eligible students selecting them by period end, and separately by students submitting a scored item for that quality in the period. Add selectedAt and stage roster history before date-filtered reporting.
ImprovementCompare the same quality across baseline and chosen stage for the same learner. Average individual percentage-point changes over matched learners only. Show matched count. No matches gives missing.
ExampleTwo eligible students, one starter and one finisher → 1/2 participation and completion. For one matched learner at 50% then 100%, average change is +50 points (n=1).
