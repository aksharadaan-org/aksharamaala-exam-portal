Student and staff contracts

All routes below use /v1. The local student reference returns HTTP 200 on success and JSON errors shaped as {"error":"code"}. Protected routes take Authorization: Bearer <token>. The request examples use invented IDs.

How to read an API call

An API call is a message from the app to the server. GET reads, POST starts an action, PUT saves a value, PATCH changes a profile, and DELETE signs out. The path after /v1 tells the server which action to perform.

Working student routes The student routes in the first tables exist in api/server.mjs. Planned staff routes The staff routes at the bottom are requirements for future work and will not respond in the current server.

One request from start to finish

The student chooses Baseline. The app sends the request below with the token from sign-in. The server replies with an attempt ID. Save that ID and use it to read questions and save answers.

POST http://127.0.0.1:4177/v1/attempts
Authorization: Bearer <demo token>
Content-Type: application/json

{"stage":0}

Response: {"id":"<attempt ID>"}

Here 0 means Baseline, and {id} in later routes means the ID returned above. If you send the same start request again, the API gives back the same attempt instead of creating a second one.

Common errors: 401 means sign in again; 404 means the record is absent or belongs to another student; 409 means the action conflicts with the current stage or attempt state; 422 means the input is invalid. Show a useful message and keep the student's unfinished input.

Staff service design

These endpoints describe the target staff implementation. School viewers have one school scope. Programme administrators can edit published content through versioned drafts. Resolve scope from the server session before applying query filters. The local student service currently accepts student sessions only.

EndpointBody or queryRequired behavior
